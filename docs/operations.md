# モック版の起動と運用

## 起動

Python 3.12以上とuvを使う。初回だけ `uv sync --locked` で依存を導入する。モック利用はインターネットとAPIキーを必要としない。

```sh
uv run manga init
uv run manga web
```

別のターミナルでワーカーを起動する。

```sh
uv run manga worker
```

ブラウザで http://127.0.0.1:8765 を開く。保存先はmacOSでは `~/Library/Application Support/manga-drawing`、Linuxでは `~/.local/share/manga-drawing`。変更する場合は両ターミナルで同じ `MANGA_DATA_DIR` を設定する。クラウド同期フォルダーやネットワークドライブは保存先にしない。

Webを閉じてもワーカーは動く。ワーカーが停止したら同じコマンドで再起動する。ロックを削除して二重起動しない。`Ctrl+C`で停止でき、送信済みの模擬処理は次回に回収する。

## 試す

```sh
uv run manga example --output /tmp/manga-example --pages 3
```

作品登録でこのフォルダーを選ぶ。manifest.jsonと画像3枚を検証して登録し、未生成ページを生成する。サンプルはプログラムで作った試験画像であり、漫画原稿やAI作画ではない。

ページ詳細で候補を採用するか、修正内容を書いて「却下して保存」「修正して再生成」を使う。一覧から要修正ページだけをまとめて再生成できる。全文編集、過去候補、障害時の操作は詳細領域に置いている。

## 入力と更新

manifestの形式は `uv run manga example` の出力を参考にする。PNG/JPEG、1ファイル20MiB、登録1回1GiB、画像40MP、作品500ページまで。フォルダー相対パスで指定する。ZIP入力は非対応。サブフォルダーがある作品はフォルダー選択を使う。

作品設定から同じ作品へ再登録すると同番号ページのdraftを更新し、採用と生成履歴は保持する。共通人物資料の変更は次回の生成だけに反映する。原稿画像の差し替えは再登録、人物とシーンの説明は資料の詳細から編集する。

## エラーへの対処

| 表示 | 操作 |
| --- | --- |
| ワーカー停止中 | 別ターミナルでmanga workerを起動 |
| 送信枠不足 | 一覧の詳細から送信件数を追加。モック版の枠は試験用で、課金はない |
| 結果確認が必要 | 外部処理の再照合を使う。0件でも勝手に再送しない |
| 結果キー異常 | 同じ結果の再取得を試す。解決しなければ重複の可能性を理解して明示再送 |
| 生成の確定失敗 | 詳細で再試行。演出を変える場合は却下して修正再生成 |
| 編集競合 | 未保存の文字を退避し、再読み込み後に他の変更を確認して入力し直す |
| 画像欠損 | doctorとバックアップを確認。ワーカーは同じ外部結果から再取得する。採用を自動変更しない |

通信応答が失われた生成操作はsessionStorageに同じ操作キーとpayloadを保持する。元の操作ボタンを再度押すと同じ要求を照合する。タブを閉じるとsessionStorageは失われるため、その場合は一覧で処理結果を確認してから追加生成する。

## 書き出しとバックアップ

採用画像を全ページまたは採用済み分だけ通常のフォルダーへ書き出す。画面の「画像フォルダーを開く」からFinder等で直接開き、連番PNGをそのまま使う。グレースケールPNGを比率保持・白余白で指定寸法へ変換し、原本を変更しない。manifest.jsonに採用IDとhash、未採用ページ、provider=mockを記録する。

```sh
uv run manga doctor
uv run manga backup --output /absolute/path/new-backup
```

バックアップ先は新しいフォルダーを指定する。DB、原稿、生成結果、模擬外部状態を整合した形で保存する。DBファイル単独のコピーで代替しない。

復元はWebとワーカーを停止して、空の保存先に対して実行する。

```sh
MANGA_DATA_DIR=/absolute/path/restored uv run manga restore --source /absolute/path/new-backup
MANGA_DATA_DIR=/absolute/path/restored uv run manga doctor
```

## Gemini接続

既定はmock。実接続コードの導入は`uv sync --locked --extra gemini`。リポジトリ直下の`.env`（`.env.example`をコピー）へ設定し、このディレクトリーからWebとworkerを起動する。同じ値の環境変数がある場合は環境変数を優先する。親ディレクトリーの`.env`は検索しない。

| 変数 | 内容 |
| --- | --- |
| MANGA_PROVIDER | gemini |
| MANGA_ENABLE_LIVE | 1（実送信を明示的に有効化） |
| GEMINI_API_KEY | 利用するアカウントのキー。チャット・Git・シェル履歴へ貼らない |
| MANGA_LIVE_MAX_REQUESTS | 通常利用は空欄。試験時だけ累積生成回数の上限を指定（例：3） |
| MANGA_LIVE_BUDGET_PER_IMAGE_USD | 画像1枚に見込む費用。米ドル額をそのまま入力（例：0.10） |
| MANGA_DATA_DIR | 保存先。mockとは別の専用ディレクトリーを推奨 |

上限・予算単位の値をアプリが推測して実送信することはない。初回live検証は少数の要求と明示した予算で行い、実schema・出力・利用明細を照合する。この開発環境での初回2＋修正1の機能試験は成功済み。作者による品質採否と実請求明細の照合は別途。[結果](live-acceptance-report.md)を参照。

試験用の要求上限を指定した場合だけ、DATA_DIR単位の累積値で制限する。通常利用では空欄にし、この制限を適用しない。生成操作ごとのページ数・候補数と送信の重複防止は引き続き適用する。Geminiの送信前の確定失敗と、native Batch createで未受理と確定した400/401/403/404/429は、要求枠とバッチの予算予約を返却する。返却は失敗確定と同じtransactionで一度だけ行い、監査記録と失敗履歴を残す。受理済みの要求とunknownは予約を保持する。画面の残数は予約可能数であり成功画像数ではない。複数バッチの合計が上限に達すると待機し、上限縮小後の準備済みチャンクも停止する。

予算単位は内部の予約額で、Googleの請求額を保証する金額上限ではない。実料金・利用枠は実行前に利用アカウントで確認する。SDKの自動再試行は無効。送信の成否不明時は自動再送せず照合し、重複リスクを明示した操作でのみ再送する。

既存の候補には生成元を表示し、書き出しのmanifestにも記録する。起動providerを切り替えても旧providerのジョブを別APIへ送らない。キーは環境変数またはGit対象外のローカル`.env`から受け取り、DB・アプリのバックアップ・画面へ保存しない。`.env`を使う場合は`chmod 600 .env`で本人だけが読み書きできるようにする。


### 設定場所と確認

macOSの本作業環境では`/Users/masa/マイドライブ/Dev/100-times-ai-manga-drawing/.env`に記入する。ローカルの記入用ファイルは作成済み。テンプレートではキーと画像1枚に見込むドル額の2項目が空欄。要求上限はT14用の3、保存先は`.data/live-acceptance`。本作業環境の.envはユーザー設定済みで、その内容はGitへ含めない。

```sh
# リポジトリ直下で実行する。初めて設定ファイルを用意する環境だけコピー。
cp -n .env.example .env
chmod 600 .env
# エディターで.envを編集した後、送信せず設定だけ確認
uv run --extra gemini manga live-check
```

`live-check`はSDKクライアントを作らず、キー・設定値を表示せず、データを初期化しない。既存DBがあれば読取専用で累積予約数と処理中のGeminiジョブ数を確認する。未予約の待機ジョブがある場合もT14準備完了とはしない。成功はローカル設定の充足だけを意味し、キーの有効性・実モデル・利用枠の検証ではない。

`MANGA_LIVE_BUDGET_PER_IMAGE_USD`には、画像1枚に見込む費用を米ドルで入力する。例：`0.10`は10セント、`1.00`は1ドル。単位の換算はアプリが行う。実請求の強制上限ではなく、アプリ内の予算管理に使う額。旧設定名`MANGA_LIVE_UNIT_RESERVE_MICRO_USD`は既存環境との互換用にのみ受け付ける。

設定変更は起動時に反映する。稼働中のモックをliveへ勝手に切り替えない。live確認に進む際は、同じディレクトリーからWebとworkerを再起動する。

### T14 実行順序

1. `live-check`成功後、専用保存先でinitする。2ページの資料（ネーム・指示画像・人物資料）を登録する。
2. 1候補ずつ、計2要求の計画を作り、一括送信する。外部ID・送信数・SDK版・日時を秘密情報抜きで記録する。完了待ち中の再送はしない。
3. 結果2枚を回収し、複数参照の伝達と画像schemaを確認する。作者がページ1を採用、ページ2を却下し、ページ1の採用候補IDと画像hashを記録する。
4. ページ2のプロンプトを修正し、そのページだけ1要求を送信する。総要求数3、ページ1の採用候補ID/hash不変を照合する。
5. 画像フォルダーとmanifest、エラー・再送の有無、利用明細を記録する。機械的な合格と作者による画質の採否を分け、試験結果を記録する（過去の独立確認はAIエージェントによるもの）。失敗時はunknown等の状態を維持して調査し、追加課金を伴う再試験を無断で増やさない。


### 実APIが前提条件エラーで拒否される場合

`live-check`やモデル情報取得の成功は、支払い設定の完了を意味しない。Google AI Studioの「プロジェクト」で、利用キーのプロジェクトが無料枠のままになっていないか確認する。Gemini 3 Pro Imageの無料枠は[公式料金表](https://ai.google.dev/gemini-api/docs/pricing#gemini-3-pro-image)で提供されていない。

認証・課金などによるHTTP400の拒否は自動再送しない。未受理の要求枠は返却するため、外部条件を解消した後は元の上限のまま再試験できる。旧バージョンが保持した明確な拒否の予約も、worker起動時に一度だけ回復する。失敗履歴は削除せず、単にカウンター全体をゼロにする操作はしない。unknownや受理後の失敗は返却対象にしない。


### 合成資料によるライブ受入試験の継続

`scripts/live_acceptance_flow.py`は、この開発環境の`artifacts/live-acceptance.json`に記録済みの初回2ページバッチを対象にする継続用ユーティリティ。一般の作品を自動採用する機能ではない。通常のworkerと同じ`.env`で起動する。

```sh
uv run --extra gemini python scripts/live_acceptance_flow.py
```

対象の作品・バッチ・ページ・providerを照合し、合成資料の初回2枚が回収できたら、ページ1の採用を固定し、ページ2だけ修正して1要求を登録する。API呼出しは通常workerに任せ、元の上限3を維持する。試験用の採用操作は作者の画質判定を代行せず、結果にも`author_quality_review=pending`を残す。

修正後はページ1の採用ID・画像hash不変と、最終2ページの候補ID・hashに一致する画像フォルダーを確認する。別作品や古い書き出しは使わない。record保存と固定操作キーで再起動時の重複生成を防ぎ、failed/unknownでは停止する。workerを再起動する場合も同じ保存先を使い、バッチを新規登録し直さない。

この作業環境の実API画面は`http://127.0.0.1:8766/`（`manga web --port 8766`）、既存モック画面は8765番。両者は別の保存先を使う。live試験の成功3要求は予約を消費済みであり、未受理拒否の返却とは区別する。


作品フォルダーを指定した場合、`生成結果/0001_テイク01.png` のように画像を直接保存する。出力一覧CSVでページ・テイク・候補番号を確認できる。出力中は専用の一時フォルダーを使い、画像が揃ってから最新出力に切り替える。ページ一覧を再表示しても直近の「画像フォルダーを開く」ボタンを利用できる。

## 複数作品・連載の管理

トップ画面の「作品管理」で、作品ごとに話をまとめて表示します。「この作品に話を追加」から登録すると、manifest.json の title を話名として既存作品に追加します。「新しい作品」を選べば独立した作品になります。読み切りは1作品・1話のまま使えます。各話の設定から所属作品、作品名、話名、制作状態を変更できます。

一覧は「制作中」「完了」「保管済み」「すべて」で切り替えます。各話に採用済み／全ページ数を表示します。全ページ採用済みで、処理中・結果不明の要求がない場合だけ完了にできます。保管は削除ではありません。進行中の生成はそのまま完了まで続き、新しい生成は制作中に戻してから開始します。

入力と中間生成物はアプリの保存先で管理します。同じ内容の画像はSHA-256で共用し、作品ごとの画像コピーを増やしません。新しい登録から、元のmanifest、元ファイル名、原本画像と正規化画像のハッシュの対応を input_imports に記録します。登録の更新は同じ話・ページ番号を更新し、採用画像、生成時点のプロンプト・資料の版、候補・採否履歴を残します。移行前の登録について、記録されていない元ファイル名を復元したとは扱いません。

作品フォルダーを指定した場合は、その中の「生成結果」に最新の採用画像をまとめます。未指定の場合はアプリの保存領域へ書き出します。過去の出力はアプリ側で保持し、画面には最新の完成出力を表示します。ZIPの解凍は不要です。

人物・シーン資料の編集単位は各話です。同じ作品に所属させても、他の話の資料を自動で上書きしません。同じ資料画像を複数の話に登録しても、画像本体は共用されます。作品全体のバックアップは既存の `manga backup --output 保存先` で行います（保存先全体のバックアップです）。話を保管しても原本・候補を自動削除しません。

既存DBは起動時にスキーマ2へ移行します。各既存作品を1作品・1話に対応付け、ページ・採否・生成要求のIDは変更しません。更新前にワーカーとWebを停止し、保存先をバックアップしてください。

## 一覧での採否判定とページの移動

ページ一覧には「確認待ち」「採用済み」「要修正」などの状態を表示します。候補が1枚なら、カードの「採用する」で採用、「要修正にする」で却下できます。採用済みのページを却下するボタンは「採用解除して要修正」と表示します。候補が複数ある場合は「候補を比較して採用」から詳細を開いて選びます。要修正にしただけでは有料の再生成は始まりません。

生成対象を一部に絞るときだけ「生成・再生成するページを絞る（任意）」を開きます。ここでのチェックは生成対象の指定で、採否には影響しません。表示条件を変更するか、この欄を閉じると対象指定を解除します。指定がない場合は、生成ボタンに該当する全ページが対象です。追加候補の生成には対象ページの指定が必要です。

詳細画面の上部と採否欄の下に「前のページ」「次のページ」があります。同じ話のページ番号順に移動します。入力中の修正・演出・プロンプト全文は保存してから移動し、保存の競合やエラーがある場合は現在のページに留まります。

入力資料は初期表示を指示書とし、ネームとの切り替えができます。「修正内容を保存」は修正を保存する操作で、画像の再生成は行いません。「生成の状況」には生成中・待機中の件数を表示し、異常がある場合だけ対応欄を表示します。

## 生成を開始したか・完了したかの表示

一覧と詳細では、採否の状態とは別に、今回の生成の版と進行状態を表示します。

| 表示 | 確定している状態 |
| --- | --- |
| 生成未依頼（開始操作をしていません） | 生成依頼が登録されていない |
| 依頼受付済み・API送信待ち | アプリが依頼を登録済み。APIにはまだ生成を依頼していない |
| APIへ送信中（受理は未確認） | 送信処理中。APIの受理をまだ確認できていない |
| API受理済み・生成結果待ち | APIが受理済み。完成画像はまだ取り込んでいない |
| 生成完了・画像を取得して保存中 | APIから結果が返り、画像を取り込んでいる |
| 生成完了・画像保存済み | 今回の候補画像を保存済み |
| 依頼受付済み・送信開始を一時停止中 | 依頼は登録済みだが、新しい送信を停止している |
| 送信失敗・自動再試行の開始待ち | 失敗後の再試行時刻を待っている |
| 生成失敗・処理停止中 | 該当候補の処理が失敗して停止している |
| APIの受理・完了状況が不明（要確認） | 受理・完了を断定できず、再確認が必要 |

再生成直後の画像欄に「未生成」は表示しません。今回の版に画像がなければ、その進行状態を表示します。詳細で以前の候補を表示する場合は、過去の版であることを明記します。複数候補が異なる段階にある場合は、段階ごとの件数を併記します。

再生成中に詳細画面を開いて待っている場合、今回の候補が届いた時点で表示を今回の版へ切り替えます。今回の有効な候補は「この候補を採用」で採用できます。過去候補を意図して採用する場合だけ、採用ボタンのすぐ上にある「表示中の過去候補を採用する」にチェックします。採用済みの場合は「この候補は採用済み」と表示します。

## 番号だけの指示書と文章の作画指示

初回生成前に、一覧からページを開き、通常画面の「作画指示」→「このページのプロンプト」へ、画像内の①・②などに対応する文章を入力します。「作画指示を保存」で保存し、一覧から初回生成を開始します。ページを前後に移動する場合も保存されます。別ファイルを用意する必要はありません。

再生成時も保存した作画指示を使い、「修正内容」を追加して送信します。指示の保存だけではAPIへ送信しません。保存した指示を変更しても、生成済みの画像や過去の生成条件は変わりません。どの指示で生成したかは候補ごとの保存済み指示で確認できます。

資料と一緒に文章を準備する場合は、manifest.jsonの各ページに任意の `page_prompt` 文字列を指定できます。画像資料の再登録時にこの項目を省略すれば、画面で入力済みの作画指示を保持します。明示的な空文字列は指示を消去します。

詳細設定で「全文を直接編集する」を有効にした場合は、通常の作画指示・演出・修正内容に代えて、その全文を送信します。この場合は作画指示欄のそばに警告と「通常の作画指示に戻す」ボタンを表示します。

## 作品フォルダー内の画像出力

作品設定の「保存先と出力の設定」→「作品フォルダー」を指定すると、通常使う画像はそのフォルダーの `生成結果/0001_テイク01.png` のように直接出力します。作品内に複数の話がある場合だけ、`話名/生成結果/0001_テイク01.png` として混在を防ぎます。作品ID・書き出しID・pagesという階層は、通常の出力先に含めません。

書き出し直すと、この場所を最新の採用画像に更新します。以前の出力はアプリの保存領域へ保管します。生成履歴や候補の管理に使う内部保存領域と、利用者が開く画像フォルダーは別です。作品フォルダーの原稿は移動・削除しません。


## テイク番号と却下候補

テイクはページごとの生成回です。初回はテイク1、再生成するたびにテイク2、テイク3と進みます。同じテイクで複数候補を作った場合は候補番号で区別します。採用画像のファイル名は `0006_テイク04.png`、複数候補の2枚目なら `0006_テイク04_候補02.png` です。最新の生成回ではなく、実際に採用した候補のテイクを使います。

作品フォルダーを設定した作品では、却下した画像を `却下した候補/` にテイク番号付きで保存し、`候補一覧.csv` にページ・テイク・候補・却下理由を記録します。却下によってアプリ内の画像や生成条件を削除しません。後からその候補を採用した場合は却下フォルダーから外し、アプリ側の履歴に保持します。ファイルの同期はワーカーが行い、画像生成を追加実行しません。

`生成結果/出力一覧.csv` と画面の出力欄に、書き出した採用画像のテイクを表示します。未採用ページは書き出しに含めません。
