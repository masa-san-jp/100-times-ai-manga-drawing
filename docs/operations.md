# 利用手順

## 必要なもの

- Python 3.12以上とuv
- GeminiのAPIキーと課金設定
- キャラクタースケッチ、ネーム、作画指示書、および対応付けを記述したmanifest.json

実際の作画にはGemini APIを使用し、API利用料がかかります。公開作例の閲覧にはAPIキーもアプリの起動も不要です。

## 設定場所と確認

設定はリポジトリ直下の `.env` に保存します。初回は `.env.example` をコピーし、次の2項目を記入してください。設定済みのファイルを上書きする必要はありません。

| 項目 | 記入する内容 |
| --- | --- |
| `GEMINI_API_KEY` | 自分のGemini APIキー |
| `MANGA_LIVE_BUDGET_PER_IMAGE_USD` | 画像1枚に見込む費用（米ドル）。例：`0.10` は10セント |

テンプレートの `MANGA_PROVIDER=gemini` と `MANGA_ENABLE_LIVE=1` は、そのまま使います。生成回数の試験用制限 `MANGA_LIVE_MAX_REQUESTS` は空欄にします。保存先は `MANGA_DATA_DIR` で変更できます。費用の設定はアプリ内の予算管理用で、Googleの実請求額を強制的に止める上限ではありません。

APIキーは `.env` のみに記入します。`.env` はGit対象外です。キーをREADMEや公開する作例、チャットへ記載する必要はありません。同じ名前の環境変数を設定している場合は、環境変数の値が優先されます。親ディレクトリーの `.env` は読み込みません。

## 起動

リポジトリ直下から実行します。

```sh
uv sync --locked --extra gemini
uv run manga init
uv run manga web
```

別ターミナルで、同じディレクトリーからワーカーを起動します。

```sh
uv run manga worker
```

[アプリを開く](http://127.0.0.1:8765)。Web画面は資料の登録・採否判定・指示編集を担当し、ワーカーは生成・結果回収・ファイル保存を担当します。Webを閉じてもワーカーは動き続けます。設定を変更した場合はWebとワーカーを再起動してください。

## Gemini接続

アプリはGeminiへの接続を標準とします。キーと送信設定がない状態で作画を開始することはありません。模擬APIは開発用の明示指定でのみ利用し、[開発手順](development.md)に分けています。

## 制作の進め方

1. 作品管理で資料のフォルダーを登録します。[公開作例の構成](../examples/example-001/README.md)を参考にできます。
2. キャラクター資料画面でリファレンス画像を生成し、作画に使う候補を採用します。
3. 各ページに必要な作画指示を入力し、対象ページを生成します。
4. ページごとに採用または要修正を判定します。要修正ページだけ指示を直して再生成できます。
5. 採用画像を書き出し、作品フォルダーで利用します。

## 入力と更新

manifestの形式は `uv run manga example` の出力を参考にする。PNG/JPEG、1ファイル20MiB、登録1回1GiB、画像40MP、作品500ページまで。フォルダー相対パスで指定する。ZIP入力は非対応。サブフォルダーがある作品はフォルダー選択を使う。

作品設定から同じ作品へ再登録すると同番号ページのdraftを更新し、採用と生成履歴は保持する。共通人物資料の変更は次回の生成だけに反映する。原稿画像の差し替えは再登録、人物とシーンの説明は資料の詳細から編集する。

## エラーへの対処

| 表示 | 操作 |
| --- | --- |
| ワーカー停止中 | 別ターミナルでmanga workerを起動 |
| 送信枠不足 | 生成状況で対象件数と設定した予算を確認する |
| 結果確認が必要 | 外部処理の再照合を使う。0件でも勝手に再送しない |
| 結果キー異常 | 同じ結果の再取得を試す。解決しなければ重複の可能性を理解して明示再送 |
| 生成の確定失敗 | 詳細で再試行。演出を変える場合は却下して修正再生成 |
| 編集競合 | 未保存の文字を退避し、再読み込み後に他の変更を確認して入力し直す |
| 画像欠損 | doctorとバックアップを確認。ワーカーは同じ外部結果から再取得する。採用を自動変更しない |

通信応答が失われた生成操作はsessionStorageに同じ操作キーとpayloadを保持する。元の操作ボタンを再度押すと同じ要求を照合する。タブを閉じるとsessionStorageは失われるため、その場合は一覧で処理結果を確認してから追加生成する。

## 書き出しとバックアップ

採用画像を全ページまたは採用済み分だけ通常のフォルダーへ書き出す。画面の「画像フォルダーを開く」からFinder等で直接開き、連番PNGをそのまま使う。グレースケールPNGを比率保持・白余白で指定寸法へ変換し、原本を変更しない。manifest.jsonに採用IDとhash、未採用ページ、生成元のAPIを記録する。

```sh
uv run manga doctor
uv run manga backup --output /absolute/path/new-backup
```

バックアップ先は新しいフォルダーを指定する。DB、原稿、生成結果、模擬外部状態を整合した形で保存する。DBファイル単独のコピーで代替しない。

復元はWebとワーカーを停止して、空の保存先に対して実行する。

```sh
MANGA_DATA_DIR=/absolute/path/restored uv run manga restore --source /absolute/path/new-backup
MANGA_DATA_DIR=/absolute/path/restored uv run manga doctor
```

## 複数作品・連載の管理

トップ画面の「作品管理」で、作品ごとに話をまとめて表示します。「この作品に話を追加」から登録すると、manifest.json の title を話名として既存作品に追加します。「新しい作品」を選べば独立した作品になります。読み切りは1作品・1話のまま使えます。各話の設定から所属作品、作品名、話名、制作状態を変更できます。

一覧は「制作中」「完了」「保管済み」「すべて」で切り替えます。各話に採用済み／全ページ数を表示します。全ページ採用済みで、処理中・結果不明の要求がない場合だけ完了にできます。保管は削除ではありません。進行中の生成はそのまま完了まで続き、新しい生成は制作中に戻してから開始します。

入力と中間生成物はアプリの保存先で管理します。同じ内容の画像はSHA-256で共用し、作品ごとの画像コピーを増やしません。新しい登録から、元のmanifest、元ファイル名、原本画像と正規化画像のハッシュの対応を input_imports に記録します。登録の更新は同じ話・ページ番号を更新し、採用画像、生成時点のプロンプト・資料の版、候補・採否履歴を残します。移行前の登録について、記録されていない元ファイル名を復元したとは扱いません。

登録時に自動作成した作品フォルダーの「生成結果」に最新の採用画像をまとめます。追加設定は不要です。過去の出力はアプリ側で保持し、画面には最新の完成出力を表示します。ZIPの解凍は不要です。

人物・シーン資料の編集単位は各話です。同じ作品に所属させても、他の話の資料を自動で上書きしません。同じ資料画像を複数の話に登録しても、画像本体は共用されます。作品全体のバックアップは既存の `manga backup --output 保存先` で行います（保存先全体のバックアップです）。話を保管しても原本・候補を自動削除しません。

既存DBは起動時にスキーマ2へ移行します。各既存作品を1作品・1話に対応付け、ページ・採否・生成要求のIDは変更しません。更新前にワーカーとWebを停止し、保存先をバックアップしてください。

## 一覧での採否判定とページの移動

ページ一覧には「確認待ち」「採用済み」「要修正」などの状態を表示します。候補が1枚なら、カードの「採用する」で採用、「要修正にする」で却下できます。採用済みのページを却下するボタンは「採用解除して要修正」と表示します。候補が複数ある場合は「候補を比較して採用」から詳細を開いて選びます。要修正にしただけでは有料の再生成は始まりません。

生成対象を一部に絞るときだけ「生成・再生成するページを絞る（任意）」を開きます。ここでのチェックは生成対象の指定で、採否には影響しません。表示条件を変更するか、この欄を閉じると対象指定を解除します。指定がない場合は、生成ボタンに該当する全ページが対象です。追加候補の生成には対象ページの指定が必要です。

詳細画面の上部と採否欄の下に「前のページ」「次のページ」があります。同じ話のページ番号順に移動します。入力中の修正・演出・プロンプト全文は保存してから移動し、保存の競合やエラーがある場合は現在のページに留まります。

入力資料は初期表示を指示書とし、ネームとの切り替えができます。「修正内容を保存」は修正を保存する操作で、画像の再生成は行いません。「生成の状況」には生成中・待機中の件数を表示し、異常がある場合だけ対応欄を表示します。

## 生成を開始したか・完了したかの表示

一覧と詳細では、採否の状態とは別に、今回の生成の版と進行状態を表示します。

| 表示 | 確定している状態 |
| --- | --- |
| 生成未依頼（開始操作をしていません） | 生成依頼が登録されていない |
| 依頼受付済み・API送信待ち | アプリが依頼を登録済み。APIにはまだ生成を依頼していない |
| APIへ送信中（受理は未確認） | 送信処理中。APIの受理をまだ確認できていない |
| API受理済み・生成結果待ち | APIが受理済み。完成画像はまだ取り込んでいない |
| 生成完了・画像を取得して保存中 | APIから結果が返り、画像を取り込んでいる |
| 生成完了・画像保存済み | 今回の候補画像を保存済み |
| 依頼受付済み・送信開始を一時停止中 | 依頼は登録済みだが、新しい送信を停止している |
| 送信失敗・自動再試行の開始待ち | 失敗後の再試行時刻を待っている |
| 生成失敗・処理停止中 | 該当候補の処理が失敗して停止している |
| APIの受理・完了状況が不明（要確認） | 受理・完了を断定できず、再確認が必要 |

再生成直後の画像欄に「未生成」は表示しません。今回の版に画像がなければ、その進行状態を表示します。詳細で以前の候補を表示する場合は、過去の版であることを明記します。複数候補が異なる段階にある場合は、段階ごとの件数を併記します。

再生成中に詳細画面を開いて待っている場合、今回の候補が届いた時点で表示を今回の版へ切り替えます。今回の有効な候補は「この候補を採用」で採用できます。過去候補を意図して採用する場合だけ、採用ボタンのすぐ上にある「表示中の過去候補を採用する」にチェックします。採用済みの場合は「この候補は採用済み」と表示します。

## 番号だけの指示書と文章の作画指示

初回生成前に、一覧からページを開き、通常画面の「作画指示」→「このページのプロンプト」へ、画像内の①・②などに対応する文章を入力します。「作画指示を保存」で保存し、一覧から初回生成を開始します。ページを前後に移動する場合も保存されます。別ファイルを用意する必要はありません。

再生成時も保存した作画指示を使い、「修正内容」を追加して送信します。指示の保存だけではAPIへ送信しません。保存した指示を変更しても、生成済みの画像や過去の生成条件は変わりません。どの指示で生成したかは候補ごとの保存済み指示で確認できます。

資料と一緒に文章を準備する場合は、manifest.jsonの各ページに任意の `page_prompt` 文字列を指定できます。画像資料の再登録時にこの項目を省略すれば、画面で入力済みの作画指示を保持します。明示的な空文字列は指示を消去します。

登録済みの原文は詳細画面で参照するだけです。「作画指示」「修正内容」にページ固有の指示を入力すると、原文を変更せず末尾に追記して送信します。送信内容の確認も読み取り専用です。

## 作品フォルダー内の画像出力

作品登録だけで、アプリの保存先の `作品/作品名/` に作品フォルダーを自動作成します。ページ一覧の「作品フォルダーを開く」から開けます。同名の作品は末尾に連番を付けて区別します。保存場所を変更したい場合だけ、作品設定の「保存先と出力の設定」→「作品フォルダー」で変更します。設定済みの保存場所は更新時にも維持します。

通常使う画像は作品フォルダーの `生成結果/0001_テイク01.png` のように直接出力します。作品内に複数の話がある場合だけ、`話名/生成結果/0001_テイク01.png` として混在を防ぎます。作品ID・書き出しID・pagesという階層は、通常の出力先に含めません。

書き出し直すと、この場所を最新の採用画像に更新します。以前の出力はアプリの保存領域へ保管します。生成履歴や候補の管理に使う内部保存領域と、利用者が開く画像フォルダーは別です。作品フォルダーの原稿は移動・削除しません。


## テイク番号と却下候補

テイクはページごとの生成回です。初回はテイク1、再生成するたびにテイク2、テイク3と進みます。同じテイクで複数候補を作った場合は候補番号で区別します。採用画像のファイル名は `0006_テイク04.png`、複数候補の2枚目なら `0006_テイク04_候補02.png` です。最新の生成回ではなく、実際に採用した候補のテイクを使います。

却下した画像は、作品フォルダーの `却下した候補/` にテイク番号付きで保存し、`候補一覧.csv` にページ・テイク・候補・却下理由を記録します。却下によってアプリ内の画像や生成条件を削除しません。後からその候補を採用した場合は却下フォルダーから外し、アプリ側の履歴に保持します。ファイルの同期はワーカーが行い、画像生成を追加実行しません。

`生成結果/出力一覧.csv` と画面の出力欄に、書き出した採用画像のテイクを表示します。未採用ページは書き出しに含めません。


## 画像生成モデル

新しい生成要求の標準モデルは `gemini-nano-banana-2.1`（Gemini Nano Banana 2.1）です。2K・縦3:4の画像をBatch APIで生成します。[公式モデル仕様](https://ai.google.dev/gemini-api/docs/models/gemini-nano-banana-2.1)でBatch API対応を確認しています。

保存済みの生成要求には生成時のモデルを記録します。旧 `gemini-3-pro-image` の送信待ち・処理中・復旧対象は旧モデルのまま扱い、採用済み画像や履歴を書き換えません。予算設定は利用者が指定した上限見積もりで、モデル別の実請求額ではありません。今回の変更で設定値を自動変更しません。


## キャラクターリファレンスの生成と採用

1. 通常どおりキャラクタースケッチ・ネーム・指示書を登録します。
2. ページ一覧の「キャラクター資料を開く」へ進みます。
3. 人物ごとに生成指示を入力できます。空欄でも、スケッチと人物設定からモノクロの全身正面・側面・背面と顔の設定画を生成します。
4. 「未生成・要修正の人物をまとめて生成」または人物ごとの「この人物を生成」を押します。Batch APIで処理し、送信待ち・生成中・完了を区別して表示します。
5. 生成画像を確認し、「この候補を採用する」で決定します。修正する場合は指示を保存し、人物ごとに再生成します。採用を解除して要修正にもできます。
6. ページ一覧へ戻り、ページ生成を実行します。そのページの登場人物について、採用した設定画を添付します。スケッチを代わりに添付して処理を進めることはありません。必要な人物のリファレンスが未採用なら開始できません。

設定画は `作品フォルダー/キャラクターリファレンス/人物キー/テイク01.png` に保存します。同じテイクの追加候補は候補番号を付けます。生成指示のテキストと、採否・画像ハッシュを記録した `候補一覧.json` も同じ場所に保存します。複数の話に個別の人物設定がある場合だけ、その中を話ごとのフォルダーに分けます。画像の採否を変えても過去のテイクは削除しません。

再生成している間は、既存の採用設定画を維持します。新しい候補を採用した時点で、次のページ生成から切り替わります。採用済みページや送信済み要求を自動で作り直しません。スケッチ・身長などの人物設定を変更すると、古い設定画の採用は新しい入力に対して無効になり、再生成と採用が必要です。変更のないスケッチを再登録しただけなら、採用を維持します。

失敗時は人物カードの「失敗した生成を再試行」、結果不明時は同画面の結果照会を使います。永続キュー・再起動後の回収・重複送信防止・予算管理はページ作画と共通です。リファレンス生成も画像生成APIの料金対象です。

更新時はDBをスキーマ3へ移行します。既存の作品・原稿・採用画像・生成履歴は維持します。これまでスケッチを直接使って生成したページは書き換えず、次の生成からリファレンスの採用を必要とします。


## 制作状況と次の操作

ページ一覧の「制作状況」は、キャラクター資料の採用数、ページの採用・未判定・要修正の数、書き出し状況を表示します。表示条件を絞っても、この集計は全ページを対象にします。「採否未判定のページを確認」「要修正ページを確認」から該当ページだけを表示できます。

全ページ採用済みの場合は、新たな生成ではなく書き出しへ案内します。採用候補や出力寸法を変更した後は、書き出しに変更が反映されているかを区別します。状況表示の閲覧だけで、生成・採否・書き出しは実行されません。別候補を追加する場合は、対象ページを明示的に指定します。
