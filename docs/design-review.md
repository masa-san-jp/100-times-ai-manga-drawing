# 実装仕様と実装計画の独立レビュー記録

実施日：2026年10月18日  
対象：[実装仕様](implementation-spec.md)、[実装計画](implementation-plan.md)

設計担当とは別の2名のAIレビュアーが独立して文書を読み、初回指摘、修正後の再レビュー、最終版の確認を行った。最終判定は両名ともPASS。P0、P1、未解決P2はゼロ。人間によるレビューを実施したという意味ではない。

## レビュー担当と結果

| 担当 | 識別子 | 観点 | 初回 | 最終 |
| --- | --- | --- | --- | --- |
| 信頼性レビュー | review_reliability | 課金重複、復旧、状態遷移、データ整合、自律実装可能性 | FAIL | PASS |
| プロダクトとコストレビュー | review_product_cost | 大量処理の合理性、UIの単純さ、費用制御、Issueの実行可能性 | FAIL | PASS |

P0は採用不能な根本問題、P1は実装時に課金重複、採用破壊、復旧不能、主要要件の欠落を生む問題、P2は採用を妨げない改善事項として扱った。重大指摘がある版を採用せず、両名の再確認後に最終版とした。

## 主な指摘と解決

| 指摘 | 修正 | 主な位置 |
| --- | --- | --- |
| 小さな外部バッチを少数ずつ投入すると数百ページの待ち時間が過大になる | 最大1000要求または1GiBでまとめ、同時外部8件を既定値にした。アカウント制限は先行検証し、実分割数と投入波数を表示する | 仕様7、I02、I07 |
| 修正保存から生成登録までの中断で版が進み、同じ操作を再開できない | 専用POSTで修正、却下、新ラウンド、ジョブ登録を単一DB transactionにした。失敗は全rollback、成功keyを先に照合する | 仕様10、I08 |
| 再試行用バッチと既存ジョブの所有関係が曖昧 | 再試行は元batch/jobへの新attemptとし、元バッチの予算枠を使う。専用retry APIを定義した | 仕様6と7、I06、I09 |
| 結果を逐次成功登録すると後方の重複キー検出が遅れる | 全行のキー検査と正常行の取り込みを2走査に分けた | 仕様8、I09 |
| attempt状態と破損・欠損画像の復旧が曖昧 | 状態と終端を定義し、再取得と課金生成を分離した。採用画像欠損は利用不可として採用IDを保持する | 仕様7と8、I09 |
| unknownのみのページの表示優先順位が曖昧 | 実行待ちと結果不明を分け、結果不明は「結果確認が必要」と表示する | 仕様9 |
| 同じ300ジョブの試験だけでは規模差を検出できない | 300ページ×3候補の900ジョブ試験を追加した | T01、I13 |
| 子データ更新と作品versionの関係が不明 | draft、資料、審査更新時のversion伝播と書き出し時の固定を定義した | 仕様3、I08、I12 |
| ネットワーク取得中のheartbeat停止、チャンクの部分予約、全文編集の挙動が曖昧 | heartbeatの独立更新、チャンク全件の原子的予算予約、全文上書き中の警告を定義した | 仕様2、5、6 |

## 判定の範囲

このPASSは設計文書の整合性、実装可能性、計画の妥当性に対する判定である。実装コード、実アカウントのAPI利用可否、生成品質、運用実績に対する合格判定ではない。

その後の完成範囲変更では、I02を模擬API契約、I14をモック版完成、I15を後続の実API接続へ分離した。v1モック版はT01〜T13で完成でき、実APIとSDKの検証はI15とT14で別途行う。設計のPASSを実装時の独立レビューの代わりにしない。

## モック版引き継ぎに向けた変更レビュー

APIをプレースホルダーにしたままアプリを完成できるよう、完成範囲を変更し、同じ2名が独立して再レビューした。

- I01〜I14でv1モック版を完成する。T01〜T13を必須とする。
- I15とT14は後続の実API接続とし、現在の完成条件から分離する。
- 模擬APIは永続状態、試験画像、遅延と障害scenarioを実装する。Geminiだけを無効な接続口とする。
- 通常モックは2秒完了、1秒pollとし、課金なし・実際のAI作画ではないことを明示する。
- 模擬APIのDBと結果も整合バックアップへ含め、空の保存先へ復元して処理を再開できるようにする。
- 実装担当者向けの指示文を[引き継ぎ文書](implementation-handoff.md)に追加する。

変更の初回レビューでは、mockのバックアップ対象とv1に残ったSDK試験要件に指摘があり、修正した。最終版は両名ともPASS、未解決P0・P1・P2はゼロ。判定は設計と引き継ぎ文書が対象で、アプリ実装の完了を意味しない。
