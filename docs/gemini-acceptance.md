## 実装

- google-genai 2.31.0を任意依存として固定した。既定mockはキーなしで起動する。
- 画像入りJSONL、native Batch API、非同期回収、候補登録、ページ単位の修正再生成を接続した。
- SDK自動再試行を無効化し、成否不明は照合に回す。累積要求上限とバッチ予算予約を送信前に検査する。
- Webとworkerがネットワーク待機中も書込・heartbeat・バックアップを継続できる。
- UIに稼働provider、送信予約残数、上限待ち、候補ごとの生成元を表示する。APIキーは環境変数またはGit対象外のローカル`.env`で扱う。

## 実接続の試行結果（2026年10月18日）

ユーザーによる.env設定後、ローカル事前確認は成功。公式SDKのmodels.getでキーの有効性と`models/gemini-3-pro-image`の`generateContent`・`batchGenerateContent`対応を確認した。これはモデルメタデータの取得成功であり、生成成功ではない。

| 試行 | 要求数 | 結果 |
| --- | --- | --- |
| 初回2ページ一括 | 2 | Files upload成功、入力ACTIVE。Batch createはHTTP400。外部バッチIDなし |
| 形式を公式例に合わせた1ページ診断 | 1 | Files upload成功。Batch createはHTTP400、`Precondition check failed.`。外部バッチIDなし |
| 生成なしの一覧確認 | 0 | batches.list成功、既存バッチ0件 |

試行直後は画像候補0枚、累積予約3/上限3だった。後述のユーザー指示を受け、未受理と確定した3要求の予約を回復する。上限増加・履歴削除・別保存先による回避は行わない。実請求額は未照合であり、ゼロと断定しない。外部条件が解消するまで生成要求を再送しない。

形式は公式Batch APIのInput file for imagesに合わせ、JSONLの`generation_config`とuploadの`mime_type="jsonl"`へ整えた。変更後も前提条件エラーが出ており、初回400の原因が形式だったとは断定しない。SDKメッセージから固定ラベルだけを抽出する診断を追加し、キー・URL・任意の生エラーはDBへ保存しない。

次に利用アカウントの課金・利用条件を確認する。`Precondition check failed.`だけでは原因を確定できない。当初の「上限6への増加が必要」という案内は撤回。未受理と確定した要求の予約を戻し、アカウント条件解決後は元の上限3で初回2＋修正1を再検証する。

ローカルの試験入力は`artifacts/live-input/`、試験ID記録は`artifacts/live-acceptance.json`、実データは`.data/live-acceptance/`。すべてGit対象外。APIキーは結果記録に含めない。


### アカウント画面での追加確認

Google AI Studioのプロジェクト一覧で、試験用の`100-times-ai-manga-drawing`が「無料枠」「お支払い情報を設定」と表示されることを確認した。[公式料金表](https://ai.google.dev/gemini-api/docs/pricing#gemini-3-pro-image)ではこのモデルの無料枠は提供されていない。このプロジェクトの支払い情報を設定することが次の前提条件になる。HTTP400の全原因を特定したとは扱わず、設定後の再試験で確認する。

課金設定は変更していない。APIキーの有効性やmodels.getの成功だけで有料モデルを実行可能と判定しない。ユーザーによる課金設定が必要。未受理分の回復に上限増加の承認は求めない。


## 未受理の予約を回復する仕様への修正

ユーザー指示により、未受理と確定した外部拒否を生成済み扱いで枠消費させる仕様を修正。Geminiのnative createの400/401/403/404/429と、送信前の確定失敗は要求枠・予算予約を返却する。受理後の出力失敗・タイムアウト・5xx・unknownは保持する。返却receiptと監査記録を同じtransactionに保存し、再起動や再実行で二重に返却しない。過去のattemptは保存する。

旧バージョンの明確な拒否はworker起動時に回復する。障壁の解消前に認証・課金エラーを無限再送しない。これは上限の引き上げや不明要求の無条件リセットではなく、未受理と証明できた予約だけの返却である。

実データでの回復結果：2チャンク・3要求を一度だけ返却し、予約0/上限3へ戻した。各バッチの予算予約も0。3件の失敗attemptを保持し、返却監査記録2件を保存。回復処理の再実行は返却0件で、外部生成APIは呼んでいない。外部条件とT14は未解決・未完了のまま。

予約返却の追加後、Chromiumを含む全95試験が成功。ruff check/formatも成功。
